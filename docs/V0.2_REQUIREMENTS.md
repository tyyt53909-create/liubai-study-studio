## 1. 文件用途與優先級

本文件是 DSE Study Studio 下一階段 v0.2 的開發交付要求。目標是把目前已完成的本機工程 MVP，提升為可長期使用、可安全部署、可可靠保留一年半學習歷史的版本。

本文件只定義「需要完成什麼」與「如何驗收」，不要求額外擴張產品範圍。除本文件明確要求外，現有已驗收行為應保持不變。

## 2. v0.2 的目標

v0.2 不以新增大量功能為目標，而是補足長期使用所需的底層能力。完成後，系統至少要可靠回答「做過什麼、什麼時候做、這個月完成多少任務、任務是否曾改期」，並可在私人部署環境中安全接收提醒。

- 建立可靠的 Task History / Task Event 歷史。
- 讓任務完成、取消、改期等關鍵事件可以被查詢與統計。
- 把提醒機制提升到可實際依賴的程度，避免重複通知並支援點擊直達任務。
- 具備單一使用者的安全部署能力，不暴露私人學習資料。
- 降低目前大型單文件對後續 Codex 開發的維護風險。
- 避免隨歷史資料增加而持續全量下載所有任務、Interval、Review 與事件。

## 3. 必須維持的產品邊界

| 項目 | 要求 |
| --- | --- |
| 決策權 | 使用者決定讀什麼與何時做；系統不自動安排。 |
| 任務時間 | 維持 UNSCHEDULED / MONTH / WEEK / DAY / FIXED 五種語義。 |
| 複習紀錄 | Review 只代表已記錄的學習活動，不代表掌握度或成效判定。 |
| 通知 | 只有使用者明確設定 Reminder 才通知。 |
| 學習狀態 | 維持單一 active session；Pause 不計時；Stop 保存進度；Continue 可延續。 |
| 介面風格 | 維持繁體中文、平靜、簡潔、非企業儀表板方向。 |
| 時區 | 所有產品日期語義維持 Asia/Hong_Kong，星期一為一週開始。 |

不得藉 v0.2 將產品改造成自動排程器、AI 學習顧問、遊戲化工具或完整筆記軟體。

## 4. P0 — Task History 與 Task Event

這是 v0.2 的最高優先級。現有任務只有 created_at 與 status，無法可靠回答任務真正完成或取消的時間，也沒有保存改期歷史。v0.2 必須補足此能力。

### 4.1 Task 必須新增的長期欄位

| 欄位 | 要求 |
| --- | --- |
| updated_at | 保存任務最後一次有效更新時間。 |
| completed_at | 首次真正完成任務的時間；未完成保持 null。 |
| cancelled_at | 首次真正取消任務的時間；未取消保持 null。 |

### 4.2 Task Event 必須存在

新增不可變的任務事件歷史。事件至少需要支援以下種類：

```text
CREATED
PLAN_CHANGED
SESSION_STARTED
SESSION_STOPPED
COMPLETED
CANCELLED
```

- 每個事件必須有獨立 id、task_id、事件類型、發生時間。
- PLAN_CHANGED 必須保存變更前與變更後的 level、on_date、fixed_time。
- SESSION_STARTED / SESSION_STOPPED 應能關聯對應的 Session。
- 事件資料必須可支援之後的歷史頁、月份統計與任務時間線。
- 重複提交相同的完成、取消或已經成立的狀態，不得產生重複事件。
- 沒有實際變化的安排儲存不得製造無意義的 PLAN_CHANGED。

### 4.3 舊資料處理

- 既有 Task、Session、Interval、Review、Reminder 必須完整保留。
- 不得用 created_at 或其他推測值偽造舊任務的 completed_at / cancelled_at。
- 無法確定的舊完成時間保持未知，介面需要能合理表示「v0.2 前，精確時間未知」。

## 5. P0 — 任務紀錄介面

目前的「複習紀錄」應保留，但 v0.2 必須新增真正的「任務紀錄」。兩種紀錄不能混為同一概念。

### 5.1 History 頁

- History 必須可在「任務紀錄」與「複習紀錄」之間切換。
- 任務紀錄至少支援：全部、本週、本月。
- 任務紀錄至少可按 Subject 篩選。
- 任務紀錄至少顯示任務名稱、科目、事件或完成狀態、發生時間。
- 本月完成任務數只能以 completed_at / 完成事件計算，不得以 created_at 推算。
- 取消任務與完成任務必須區分。
- 歷史資料是按需查看，不要把大量歷史統計主動塞到 Today 首頁。

### 5.2 Task Detail 歷史

- 任務詳情需要能查看該任務的關鍵時間線。
- 時間線至少涵蓋建立、安排/改期、學習開始/停止、完成或取消。
- 現有 Review 邏輯不應被 Task Event 取代；兩者保持獨立。

## 6. P1 — Reminder 可靠性

v0.2 的 Reminder 需要從「本機驗證可用」提升為「私人部署後可以實際依賴」。

- 同一 Reminder 在開頁輪詢與 Web Push 同時存在時，不得重複送達。
- Reminder 必須有清楚且可追蹤的 pending / claimed-or-sending / delivered / error 語義，確保一次性送達。
- 應用或伺服器在提醒時間後恢復時，仍應把尚未送達的 Reminder 補送一次。
- Task 完成或取消後，未送出的 Reminder 不得再通知。
- 修改同一 Task 的 Reminder 時，只保留新的有效提醒。
- 失效或已不存在的 Web Push subscription 必須可被清理。
- Notification click 必須開啟或聚焦 Study Studio，並直接定位到對應 Task Detail。
- 若需要先登入，登入成功後應回到原本通知指向的 Task。
- 通知權限被允許不等於 Reminder 已送達，兩者狀態不得混淆。

### 6.1 真機驗收

- 在 HTTPS 私人部署環境，以實際手機與支援的瀏覽器完成背景通知驗收。
- 至少驗證一次「網站未保持前景 → 到時收到通知 → 點通知 → 進入對應任務」。
- 驗收結果與已知平台限制寫入 ACCEPTANCE / README。

## 7. P1 — 單一使用者安全部署

v0.2 只需要私人單人使用，不建立完整會員系統。公開或遠端部署時，未授權使用者不得讀取或修改任何學習資料。

- 加入單一使用者登入與登出。
- 除健康檢查與登入所需端點外，所有私人資料 API 必須要求有效登入狀態。
- 所有寫入 API 必須受同一存取控制保護。
- 登入狀態必須使用安全的伺服器端信任機制；不能只靠前端隱藏頁面。
- 生產部署必須使用 HTTPS。
- PostgreSQL 不得直接暴露到公網。
- VAPID 私鑰、登入憑證與其他 secrets 不得提交到 Git。
- 生產環境不得沿用示例預設密碼作為實際安全憑證。
- 登出後原 session 不得繼續存取私人 API。
- 現有 Origin / Sec-Fetch-Site 檢查可保留，但不得被視為登入驗證的替代品。

不需要：註冊、多人帳號、角色、組織、社交、邀請、Email 驗證。

## 8. P1 — 長期資料載入與 API 邊界

目前前端會週期性取得完整 state。v0.2 需要避免歷史資料隨一年半使用量增加後仍在每次 refresh 全量傳輸。

- Today / Active Session 所需資料與歷史資料必須有明確邊界。
- 前端初始載入與 15 秒刷新不得無上限下載所有歷史 Session、Interval、Review、Task Event。
- History 必須按需載入，且結果需要有明確的數量限制或分頁能力。
- Subject 的最近複習查詢不得要求下載整個一年半 Review 歷史才能顯示。
- Active Timer、Today Capacity 與未完成 Task 的現有反應速度不得因歷史資料增加而顯著下降。
- API 回傳內容只包含目前畫面需要的資料；不要求改用 GraphQL、WebSocket 或其他新技術。

## 9. P1 — 代碼邊界整理

需要降低目前 src/main.tsx 與 server/index.ts 過大的維護風險，但這次不是架構重寫。

- 前端按現有產品功能邊界拆分 Today、Tasks、Planning、Subjects、History、Settings、共用 API/時間工具。
- 後端按 Tasks、Sessions、Reviews、Reminders、Settings/Subjects 等功能邊界拆分路由與服務責任。
- 共享 Domain type 與資料庫欄位保持一致；移除或修正目前沒有真實資料來源的 Task.actual 類型漂移。
- 不得因拆分改變現有 UI 視覺語言與已驗收核心互動。
- 不得在 v0.2 為了重構改框架、引入 ORM、改成微服務或重新設計整個資料層。

## 11. 驗收標準

### 11.1 Task History

- [ ] 新建 Task 後存在唯一 CREATED 事件。
- [ ] UNSCHEDULED → WEEK → DAY → FIXED 的實際變更有正確 PLAN_CHANGED 歷史。
- [ ] 重複儲存完全相同安排不產生重複事件。
- [ ] 真正完成 Task 後 completed_at 正確，並只有一個對應 COMPLETED 事件。
- [ ] 重複 complete 請求保持冪等，不產生第二個完成事件。
- [ ] 取消 Task 後 cancelled_at 正確，並只有一個 CANCELLED 事件。
- [ ] 本月完成數以 completed_at 計算。
- [ ] 舊 completed / cancelled Task 不偽造精確時間。

### 11.2 Reminder

- [ ] 同一 Reminder 即使 Browser poll 與 Web Push 競爭，也只出現一次使用者可見通知。
- [ ] 完成或取消 Task 後不再收到該 Task 的未送提醒。
- [ ] 修改 Reminder 後只會按新時間通知。
- [ ] 通知點擊後可進入對應 Task。
- [ ] HTTPS 真機背景通知至少有一條完整 PASS 證據。

### 11.3 Access Control

- [ ] 未登入存取私人 API 被拒絕。
- [ ] 登入後可正常使用現有全部功能。
- [ ] 登出後舊 session 不能繼續讀寫私人 API。
- [ ] 生產部署資料庫沒有公網 port。
- [ ] repo 與生成的前端 bundle 不包含 VAPID private key 或實際登入 secret。

### 11.4 Regression

- [ ] 現有 A–J 功能驗收保持通過。
- [ ] 現有 unit / PostgreSQL API integration test 保持通過。
- [ ] 新增 Task Event、History、Auth、Reminder concurrency 對應自動測試。
- [ ] npm run build、npm test、Docker production build / restart / persistence 驗收通過。
- [ ] 備份與還原流程涵蓋新增的歷史/驗證相關持久資料。

## 13. Definition of Done

只有同時滿足以下條件，v0.2 才算完成：

- [ ] 使用者可以可靠查到任務完成時間與本月完成數。
- [ ] 任務改期歷史被保存，且不需要使用者手動記錄。
- [ ] Review 與 Task History 概念保持分離。
- [ ] Reminder 在私人 HTTPS 部署下可實際背景送達，且不重複。
- [ ] 未授權者無法讀取或修改任何私人學習資料。
- [ ] 歷史資料不再無限制進入週期性完整 state refresh。
- [ ] 現有核心流程與 A–J 驗收無 regression。
- [ ] 文件與測試反映真實行為，不宣稱未實測能力已完成。
